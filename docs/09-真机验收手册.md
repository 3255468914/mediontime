> **这份文档解决的问题**：项目里积了一堆「未闭环」，散在四份文档里 ——  
> `03` §四/§五（无障碍人工 6 项、真机 5 项）、`05` §7（移植后必测 4 件事）、

## 0. 使用前必读

### 0.1 三条铁律

1. **只看设备，不看代码。**  
   凡是以「我读了源码，应该没问题」为依据的判断，一律不算证据。  
   本项目的自动化测试已经证明了「源码里写对了」，真机验收要证明的是**另一件事**。
2. **每项必须留证。**  
   至少四要素：设备型号 + ROM 版本、系统时间、操作录屏（或分步截图）、结论。  
   没有证据的「通过了」，下一个人会重新怀疑一遍，等于没做。
3. **「看起来正常」不是通过。**  
   本项目历史上最贵的一批缺陷（P8 那三条）全部是**不报错、不崩溃、界面还显示成功**的那种。  
   所以每一项下面都单列了一栏「**常见假通过**」——那一栏写的正是最容易骗过执行者自己的情形。  
   做的时候请对着那一栏反问一遍：「我现在看到的，会不会正好是它？」

## 1. 前置准备

### 1.1 你需要什么

**硬件**

- Android 真机 **≥ 1 台**。强烈建议 **2 台不同厂商 ROM**：  
  国产 ROM（小米 / 华为 / 荣耀 / OPPO / vivo）对后台与自启动的管控差异极大，  
  同一份代码在一台机器上准、在另一台上静静的晚 20 分钟，是**常态而不是意外**。  
  D-01 与 D-02 是最容易在这里翻车的两项。
- 若要验 iOS：一台 iPhone + 一台 macOS（Xcode 只能在 macOS 上跑）。

**开发机**

- Node ≥ 18
- Android 路线：Android Studio（含 SDK），**或不装它用命令行工具链**——本机已实测可行，见 §1.4 开头的更新说明
- iOS 路线：Xcode ≥ 15

**线材与网络**

- 一条**能传数据**的 USB 线（只能充电的线会让你对着 `adb devices` 空输出怀疑人生）
- 仅 C-01 需要：一个可解析的域名 + 一台能跑 Node 的公网服务器

### 1.2 一次性环境准备

在手机上：

1. 打开开发者选项（各厂商路径不同，一般是「关于手机 → 连点版本号 7 次」）
2. 打开 **USB 调试**；小米等 ROM 还需额外打开「**USB 调试（安全设置）**」，否则装不了包
3. **把系统时间设为自动（网络时间）**。这一点别跳过：本项目所有「什么时候该响」的判断  
   都基于本地时钟，手机时间偏 3 分钟会让 D-01 ~ D-05 的结论整体失真。
4. **先不要把应用加入任何省电白名单**。  
   D-01/D-02 要在「默认状态」下测；如果一开始就给了白名单，  
   测出来的是「加了白名单之后能响」，而用户装完应用时并不是这个状态。  
   （白名单作为**失败后的补救手段**来验证，见 D-01 的失败排查。）

在开发机上验证工具链：

```bash
adb version
adb devices          # 应列出你的设备，状态为 device；若是 unauthorized，去手机上点「允许调试」
node -v
```

> 若 `adb devices` 显示 `unauthorized`：解锁手机屏幕，会弹出授权对话框，勾选「始终允许」。

### 1.3 先跑通「正常路径」，再去测异常路径（**顺序不能反**）

D-01 测的是「应用被杀之后还能不能响」，D-02 是「重启之后」。  
但如果**连「应用开着时能不能响」都没验过**，D-01 失败时你无法区分两种完全不同的根因：

- 是真的「被杀导致不响」？
- 还是**从来就没响过**（权限没给、渠道没建、闹钟压根没注册）？

这就是 §8-D 那张分诊表要解决的问题——但前提是你先有一个**已知成立的基线**。

#### D-00 · 基线：应用打开状态下的到点提醒

> 不是 DoD 项，但**不做这一步，D-01 ~ D-05 的结论都不可信**。

**步骤**

1. 打开应用，完成免责声明勾选（或带参数 `auto=1` 跳过引导）。
2. 药品页新建一条测试计划：**每日 1 次**，时间设为「现在 + 4 分钟」。
   - 为什么是 1 次而不是 3 次：一条提醒的链路最短，出问题时少两个变量。
   - 为什么是 4 分钟：留出你自己走到设置页的时间。
3. 打开「我的 → 提醒可靠性」，截图（这张图后面 D-03 还要对照）。
4. 保持**应用在前台**，等 4 分钟。

**判定（通过条件）**

- [ ] 到点时应用内出现提醒（L1）
- [ ] 同时出现系统通知栏通知（若通知权限已授予）
- [ ] 时间偏差在你自己能接受的范围内（前台路径通常应接近准点）

**必须留证**

- [ ] 「提醒可靠性」卡片截图
- [ ] 到点瞬间的录屏（含系统状态栏时间）
- [ ] 记录实际触发时刻与设定时刻的差值：设定 `____` · 实际 `____`

**常见假通过**

> 「我设了 4 分钟，然后一直盯着屏幕，到点时响了」——  
> 这证明的是**页面内定时器**在工作，而**不是系统闹钟**在工作。  
> 两者是完全不同的代码路径（`WebPlatform` vs `NativePlatform`）。  
> 区分方法见下面 D-00 的附加检查。

**附加检查（把「页面内定时器」和「系统闹钟」分开）**

看「我的 → 提醒可靠性」卡片的第一行标题：

| 卡片第一行显示          | 意味着             | 此时 D-00 证明的是   |
| ---------------- | --------------- | -------------- |
| `页面内提醒` / `同步中…` | 跑在浏览器 / 系统闹钟没接上 | **只**证明了页面内定时器 |
| `系统已托管 N 条`      | 提醒已交给操作系统       | 证明了系统闹钟链路      |

如果这一行显示的不是「系统已托管 N 条」，**先别往下做 D 组**——  
你测的是一个不打算上线的路径。

#### 1.3.1 「提醒可靠性」页逐行核对表

打开「我的 → 提醒可靠性」，点「查看详情」，逐行核对。  
下面**左侧文案是从代码 `platform.js diagnose()` 里逐字抄出来的**，不是凭印象写的，  
所以「对不上」本身就是一条缺陷记录。

| 页面标签              | Android 原生下应显示                        | 若不符，可能的原因                                                  |
| ----------------- | ------------------------------------- | ---------------------------------------------------------- |
| 通知权限              | `已授权`                                 | 未授予 → `尚未授权，提醒无法送达`；被拒 → `已被拒绝，需到系统设置中手动开启`                |
| 系统级闹钟             | `提醒已交给系统，不依赖应用处于打开状态`                 | 显示 `浏览器关闭后无法提醒，需使用原生版本` = **跑在 Web 平台**，安装包有问题             |
| 应用被关闭后仍能提醒        | `由操作系统调度`                             | 显示 `页面关闭即失效（Web 平台限制）` = 同上                                |
| 设备重启后自动恢复         | `开机广播会自动恢复待触发提醒`                      | Android 显示 `不支持，重启后需手动打开应用` = `RECEIVE_BOOT_COMPLETED` 没生效 |
| 精确闹钟授权（仅 Android） | `系统允许按精确时刻唤醒`                         | `未授权，提醒时刻会被系统推迟（最长可达数十分钟）` 或 `无法确认，请到系统设置中检查`              |
| 省电模式下的送达          | 恒为提示项：`设备进入 Doze 后，系统对唤醒型提醒有 9 分钟节流…` | 这一行**永远显示为提示（!）而不是对勾**，属正常设计，不是缺陷                          |

弹层底部还会显示运行环境（如 `Android · 系统级闹钟（可托管上限 512 条）`）与  
`已托管提醒覆盖到 <日期> <时间>`。

### D-01 · 应用被杀后仍准时提醒

> **本节曾于一版手册中把 `am force-stop` 当作测试手段，那是错的，2026-10-11 修正。**  
> Android 平台行为：`force-stop`（含设置里的「强制停止」）会把应用置入 stopped 状态，  
> 系统**随之移除它的全部已注册闹钟**，并拒绝投递一切广播，直到用户手动打开应用——  
> 这是平台级设计，对任何应用都成立（微信也做不到）。  
> 所以「force-stop 后仍提醒」**不是本应用该满足的验收条件**，用它测只会得到必然失败。  
> 本项真正对应的是真实世界的两种进程死亡：**低内存被杀**与**用户划掉最近任务**——  
> 这两种都不会清除已注册的闹钟。要测 force-stop 场景，结论只可能是  
> 「平台清掉了闹钟」，如实记录为平台边界即可，不算缺陷。

**目的**：验证提醒的触发权已经真正交给了操作系统——进程死了，系统侧的闹钟还在，  
到点时系统自己拉起进程把通知发出来。这是 DoD 第 3 条「应用被杀死后，提醒依然触发」的直接检验。

**前置**：D-00 已通过；「提醒可靠性」显示「系统已托管 N 条」。

**步骤**

1. 先把提醒建好：新建一条「现在 + 4 分钟」的提醒。  
   （**必须在杀进程之前建**——被杀的应用无法注册新闹钟。）
2. 确认系统侧确实排着闹钟，并**截图/抄录**：
   ```bash
   adb shell dumpsys alarm | grep -i cn.mediontime
   ```
3. 杀死进程（**用 `am kill`，不是 `am force-stop`**）：
   ```bash
   adb shell am kill cn.mediontime.app
   ```
   没有 adb 时的等价做法：在「最近任务」里把应用划掉  
   （标准 Android 行为是仅移除任务、闹钟保留；个别 ROM 会深度清理，见排查表）。
4. 确认进程真的没了：
   ```bash
   adb shell ps -A | grep mediontime
   # 期望：没有任何输出
   ```
5. **关键分诊点**——再查一次闹钟：
   ```bash
   adb shell dumpsys alarm | grep -i cn.mediontime
   # 期望：仍有输出（am kill 不清除闹钟）
   # 若这里已经没有输出 → 闹钟被清是异常，进入排查表第 1 行
   ```
6. 熄屏，把手机放在一边，**不要打开应用**，等它响。

**判定（通过条件）**

- [ ] 到点后系统出现通知（通知栏 / 锁屏 / 横幅，取决于通知渠道等级）
- [ ] 期间从未打开过应用（用录屏证明）
- [ ] 触发时刻与设定时刻的偏差记录在案

**必须留证**

- [ ] 第 4 步 `dumpsys alarm` 的输出（证明闹钟确实注册在系统侧）
- [ ] 到点瞬间的录屏（**全程不打开应用**，含锁屏状态下的通知）
- [ ] 实际偏差：设定 `____` · 实际 `____`

**常见假通过**

> **① 「我用 force-stop 测，没响，所以不达标」** ——  
> 倒过来了：force-stop 后不响是**平台保证的行为**（闹钟被系统移除），不是应用缺陷。  
> 本项判定只认 `am kill` / 划卡片这两种死亡方式。  
> 想留 force-stop 的证据也可以：杀完立刻 `dumpsys alarm`，输出为空就是平台清钟的直接证据，  
> 记录为「平台边界：force-stop 后无法提醒（Android 设计如此）」。
>
> **② 「我从最近任务划掉了，然后它响了」——在标准 Android 上这本来就是有效的测试**，  
> 不是假通过。（旧版手册这里写反了。）真正要防的是另两个坑：  
> 打开应用会导致 `boot()` 重新同步闹钟（见 ③）；  
> 部分深度定制 ROM 划卡片 = 深度清理（见排查表第 4 行）。
>
> **③ 「我在等的过程中忍不住点开应用看了一眼」** ——  
> 一旦打开，应用会 `boot()` 并重新同步闹钟，于是你验证的变成「重新打开之后能响」。  
> 这一条必须靠**不碰手机**来保证；做不到就用录屏，让录像替你证明你没碰。
>
> **④ 「通知栏有记录，说明响了」** ——  
> 通知可能是应用下次打开时补发的（它会显示成「稍早的提醒」这类形态）。  
> 判断依据应该是**通知出现的时间戳**，而不是「后来在通知栏里看得见」。

**失败排查（按顺序，别跳）**

| 症状                              | 先看这里                             | 常见根因                                                           |
| ------------------------------- | -------------------------------- | -------------------------------------------------------------- |
| 杀进程后 `dumpsys alarm` 就没有该应用的输出了 | 用的是 `force-stop` 还是 `am kill`？   | `force-stop` 清钟是平台行为（见上方修正框）；`am kill` 后也没了才是异常——查插件版本与本应用通知实现 |
| 完全不响（杀后闹钟仍在）                    | 设置页「提醒可靠性」是否仍显示「系统已托管 N 条」       | 闹钟在但 ROM 杀掉后拒绝拉起 → 在系统里允许「自启动 / 后台运行」或锁定卡片再测，并把「加白名单才通」如实记进结论  |
| 完全不响（杀前就没输出）                    | D-00 是否通过、`dumpsys alarm` 杀前有无输出 | 从未注册成功 → 回 D-00 查权限与渠道                                         |
| 晚几分钟响                           | 「精确闹钟授权」是否为 `已授权`                | 未授权 → 系统把精确闹钟降级，见 D-03                                         |
| 有震动无声音                          | 系统「通知渠道」设置里该渠道是否被单独静音            | 渠道重要性被降过（渠道等级**创建后只能降不能升**，见 `05` §5.1）                        |
| 划卡片后不响、`am kill` 后正常            | ROM 是否在划卡片时做深度清理（小米/华为常见）        | 这属于 ROM 行为：改用 `am kill` 留证；同时把「划卡片会被清理」如实记入结论并建议用户锁定卡片         |

### D-02 · 设备重启后仍准时提醒

**目的**：验证开机后待触发提醒被恢复。对应 DoD 第 2 条。

**前置**：D-01 已通过。

**步骤**

1. 新建一条提醒，时间设为「**重启完成 + 5 分钟**」之后  
   （重启耗时因机而异，宁可留宽一点，比如设成重启后的第 8 分钟）。
2. 确认闹钟已注册：
   ```bash
   adb shell dumpsys alarm | grep -i cn.mediontime
   ```
3. 重启：
   ```bash
   adb shell reboot
   # 或手动重启，或 adb reboot 后等它自己起来
   ```
4. **重启完成后不要打开应用**，通过 `adb` 确认系统侧闹钟已经回来了：
   ```bash
   adb shell dumpsys alarm | grep -i cn.mediontime
   ```
5. 等它响。

**判定（通过条件）**

- [ ] 重启后（**未打开应用**）`dumpsys alarm` 中能看到该提醒
- [ ] 到点后系统出现通知
- [ ] 从重启完成到触发，全程未手动打开应用

**必须留证**

- [ ] 重启前后的两次 `dumpsys alarm` 输出（对比）
- [ ] 重启+触发的完整录屏（可以在锁屏界面录，重点是**没有打开过应用**）
- [ ] 设备重启耗时与触发偏差

**常见假通过**

> **① 「重启后我自己点开应用看了一眼，然后它响了」** ——  
> 打开应用会触发 `boot()` 里的重新同步，闹钟是**你点开之后才补上的**。  
> 这条路径证明了「打开后能恢复」，证明不了「开机自动恢复」。  
> 本项的核心判据是第 4 步那句「**未打开应用**」。
>
> **② 「重启太快，我还没等到就又点开了」** —— 重启后系统要花时间走完开机流程，  
> 开机广播到达的时间也不确定。把提醒时间设得离重启完成远一点（8~10 分钟），  
> 并接受「这段时间内不能碰应用」这个约束。
>
> **③ 只有 Android 会走这条路**：iOS 由系统持久化待触发请求，**没有开机广播**。  
> 在 iOS 上做本项时，判据应改为「重启后未打开应用，通知仍按时到达」，  
> 不要去找一个不存在的开机广播。


**失败排查**

| 症状                       | 常见根因                                                            |
| ------------------------ | --------------------------------------------------------------- |
| 重启后 `dumpsys alarm` 无该提醒 | `RECEIVE_BOOT_COMPLETED` 未声明，或补丁没跑到清单里（跑 `npm run patch:check`） |
| 部分提醒回来了、部分没回来            | 超出可托管上限被截断（Android 上限 512、iOS 64），属预期 → 看设置页是否有「推迟 N 条」提示       |
| 回来了但时间漂移                 | 手机时区/时间在重启后变化，应用按「跟随本地时间」策略平移过（见 BR-05 时区策略）                    |

### D-03 · 精确闹钟被关闭

**目的**：这是整个产品**最容易「看起来正常但实际不响」**&#x7684;地方。  
Android 12+ 的精确闹钟是**独立开关而不是普通权限**，关掉之后  
**系统不会报错，只会把提醒静默降级为「大概那个时间段」**。  
应用必须①尽量准时，②降级时如实告诉用户。

**前置**：D-00 ~ D-02 已通过。

**步骤**

1. 先记录「开着」时的基线：新建一条「现在 + 3 分钟」提醒，确认它准点响。
2. 关闭精确闹钟。两条路径二选一：
   - 手机端：`设置 → 应用 → 药准时 → 闹钟和提醒`，关闭
   - 或 adb（部分 ROM 需要 root，先试免 root 的写法）：
     ```bash
     adb shell appops get cn.mediontime.app SCHEDULE_EXACT_ALARM
     # 期望在授权状态下看到 MODE_ALLOWED（不同 ROM 文案可能不同）
     ```
3. 关闭后，**重新打开应用**（这一步是必要的：官方文档说明关闭精确闹钟时  
   系统会重启应用并删除所有已排的精确闹钟，应用启动后必须重新同步一次）。
4. 看「我的 → 提醒可靠性」：
   - 「精确闹钟授权」这一行应变成 `未授权，提醒时刻会被系统推迟（最长可达数十分钟）`
   - 并且按钮区应出现一个 **`开启精确闹钟`** 按钮
5. 新建一条「现在 + 3 分钟」的提醒，观察实际触发时刻。

**判定（通过条件）**

- [ ] 设置页**如实报出**「精确闹钟授权」为未授权（**这一条是本项的重点**）
- [ ] 出现「开启精确闹钟」按钮，点击能跳到系统设置页（或如实提示无法跳转）
- [ ] 提醒本身仍**会触发**，只是可能被推迟

**必须留证**

- [ ] 关闭前后的「提醒可靠性」截图（对比「精确闹钟授权」那一行）
- [ ] `appops get` 的输出
- [ ] 降级后实际触发时刻与设定时刻的差值

**常见假通过**

> **① 「我关了开关，但提醒还是准点响了，所以这项通过」** ——  
> 静默降级**不保证**每次都晚：系统可能刚好在维护窗口里准点送达。  
> 本项的**主判据是「应用有没有如实把降级说出来」**，而不是「有没有晚」。  
> 一次准点响不能推出「没被降级」。
>
> **② 「设置页没变化，说明开关没关成功」** ——  
> 也可能是**应用没重新读状态**。第 3 步的「重新打开应用」不能省；  
> 如果重开后仍显示 `已授权`，那就是一条**真缺陷**（诊断链路没接上），  
> 记进缺陷清单，不要当成操作失误。
>
> **③ 「按钮点了没反应，我手动的」** ——  
> 按钮的行为有两种合法结果：成功跳转、或如实提示「无法自动跳转，请到…」。  
> 只要**没有假装跳转成功**，都算通过。假装成功才算缺陷。

### D-04 · Doze（打盹）模式下的送达

**目的**：验证设备进入系统级省电（Doze）后，**L1 首次提醒仍能准时触发**。  
这是省电优化与提醒可靠性之间的那个真实取舍点。

**前置**：D-00 ~ D-03 已通过；手机已拔掉充电器（充电时不会进入 Doze）。

**步骤**

1. 新建一条「现在 + 5 分钟」的提醒。
2. 强制进入 Doze：
   ```bash
   adb shell dumpsys deviceidle force-idle
   ```
   > 若你的 ROM 不支持该命令（部分定制 ROM 会拒绝），退化为**物理静置法**：  
   > 断开充电、关闭屏幕、把手机放在桌上**静置 30 分钟以上**，不要碰它。  
   > 静置法更贴近真实，但耗时长且难以确认是否真的进了 Doze。
3. 确认已进入（不同 Android 版本输出不同，看到 `IDLE` 字样即可）：
   ```bash
   adb shell dumpsys deviceidle get deep
   # 或
   adb shell dumpsys deviceidle | head -20
   ```
4. 等待提醒触发。**不要点亮屏幕**（亮屏会让设备退出 Doze）。
5. 观察结束后退出 Doze 并恢复：
   ```bash
   adb shell dumpsys deviceidle unforce
   adb shell dumpsys battery reset
   ```

**判定（通过条件）**

- [ ] L1 到点时系统出现通知，**偏差在可接受范围内**
- [ ] 屏幕全程未点亮（录屏或锁屏日志证明）
- [ ] 若同时有 L2 催办：**L2 被推迟属预期**，不是缺陷

**必须留证**

- [ ] 进入 Doze 的确认输出
- [ ] 到点触发时刻与偏差
- [ ] 若 L2 也设了，记录 L2 的实际间隔（用于对照 9 分钟节流）

**为什么 L2 可以被推迟（这不是在给缺陷找借口）**

`allowWhileIdle` 有官方定义的 **9 分钟节流**：每个应用每 9 分钟只能被唤醒一次。  
而升级链路的 L1 → L2 间隔是 **5 分钟**。如果两级都加豁免，L2 会把本该留给  
当天后续服药提醒的额度吃掉——为一条催办牺牲了后面几条准时提醒。  
所以代码里**只给 L1 加豁免**（`platform.js` 的 `allowWhileIdleFor()`）。  
这项验证要验的是**这个取舍是否按设计生效**，而不是「全部都准点」。

**常见假通过**

> **① 「我只是开了系统的「省电模式」」** —— 省电模式（Battery Saver）与  
> Doze（Device Idle）**是两个不同的机制**。前者限制性能与后台，  
> 后者才是那个会推迟闹钟的休眠状态。用 `force-idle` 才能测到真正的 Doze。
>
> **② 「我中途看了一眼手机」** —— 亮屏即退出 Doze，之后响的是普通状态下的提醒。  
> 请在一次**不碰手机**的前提下完成整个观察窗口。
>
> **③ 「等了 5 分钟没响，这项失败」** —— 先确认**这个时刻系统是不是在维护窗口之外**。  
> Doze 下的唤醒会被安排进维护窗口（默认间隔逐次拉长），  
> 首次唤醒受影响最小、越往后越可能被推迟。判定前请先看 `dumpsys` 的 Doze 状态，  
> 并确认提醒时刻与进入 Doze 的先后关系。

### D-05 · 熄屏送达（应用存活 + 屏幕关闭）

> **本用例为 2026-10-11 首轮真机实测后新增。** 当天实测现象：应用开着、  
> 熄屏后到点**完全无声无横幅、亮屏后通知栏里也没有这条提醒**。  
> 该场景在 D-00（亮屏前台）与 D-01（进程被杀）之间，此前没有自己的用例——  
> 失败时容易被误报成 D-01。注意区分：**熄屏时进程还活着**是本项，  
> 进程被杀是 D-01，两者失败的分诊方向完全不同。

**目的**：验证最日常的使用路径——老人晚上把手机扣在桌上，**应用还活着、屏幕灭着**，  
到点时系统闹钟照常唤醒、通知照常发出并有声音/振动。  
WebView 内的 JS 定时器熄屏会被冻结，所以本项验证的**只能是原生闹钟链路**——  
它过了，才说明 D-00 里「系统已托管 N 条」不是一句空话。

**前置**：D-00 已通过且可靠性页显示「系统已托管 N 条」；「闹钟和提醒」权限已授予。

**步骤**

1. 新建一条「现在 + 5 分钟」的提醒（比 D-00 的 4 分钟多 1 分钟，  
   留出设置 ROM 后台白名单的时间）。
2. 熄屏前**做两件留证**：
   - 可靠性页截图（确认仍显示「系统已托管」，且托管条数包含这条新提醒）；
   - 若手机连着电脑，抄录系统侧闹钟：
     ```bash
     adb shell dumpsys alarm | grep -i cn.mediontime
     ```
     记下 `wakeUp` / 触发时刻字样——熄屏能否响，取决于闹钟是否带 `wakeUp` 标记。
3. 按电源键熄屏，把手机放在**视线外**（放在视线内会忍不住中途点亮看，见假通过②）。
4. **全程不碰手机**，等它响。若设置了另一台设备/手表，离远一点，避免旁证干扰。
5. 到点后（无论响没响）再点亮屏幕，**立即看通知栏**——这条信息是分诊的关键证据。

**判定（通过条件）**

- [ ] 熄屏状态下有声音或振动（不必亮屏——L1 渠道等级为 HIGH，横幅是否弹出随 ROM）
- [ ] 亮屏后通知栏里**有**这条提醒（「当时没注意、事后能看到」算响过）
- [ ] 偏差可接受（原生闹钟路径通常应接近准点；可接受的阈值由执行者记录，建议 ≤ 2 分钟）

**必须留证**

- [ ] 熄屏前可靠性页截图（含托管条数）
- [ ] 亮屏后通知栏截图（**无论响没响都要**：响了证明送达，没响是分诊证据）
- [ ] 设定时刻 / 实际感知时刻 / 亮屏查看时刻 三个时间点

**常见假通过**

> **① 「D-00 亮屏响了，熄屏就肯定也响」** —— 反了。熄屏路径**更严格**：  
> 它要求闹钟带 `wakeUp` 标记、渠道等级足够、且 ROM 没有对该应用施加省电限制。  
> 亮屏响可能只是页面内定时器在响（见 D-00 附加检查）。
>
> **② 「我中途点亮屏幕看了一眼，到点时响的」** —— 亮屏瞬间 WebView 恢复运行，  
> 页面内定时器路径接管，你听到的可能不是系统闹钟。观察窗口内不碰手机。
>
> **③ 「之前设的那条熄屏响过，这次不测了」** —— 国产 ROM 会**动态调整**管控：  
> 连续几天没被手动打开的应用，后台限制会逐步收紧。每次验收都用新设的提醒现测。

**失败排查表**（按「亮屏后通知栏里有没有」分两大类，这是最有信息量的分界线）

| 现象                | 最可能的原因                        | 排查方法                                                                      |
| ----------------- | ----------------------------- | ------------------------------------------------------------------------- |
| 无声无横幅，**通知栏里也没有** | 闹钟根本没注册进系统                    | 可靠性页是否显示「系统已托管」？没有 → 回 D-00 查通知权限与渠道；`dumpsys alarm` 无输出 → 同上             |
| 无声无横幅，**通知栏里也没有** | 「闹钟和提醒」（精确闹钟）权限未授予            | 可靠性页「精确闹钟授权」行；未授予时闹钟降级为不精确，熄屏下可被推迟很久甚至整段丢弃                                |
| 无声无横幅，**通知栏里也没有** | ROM 省电策略拦截（OPPO/vivo/小米/华为常见） | 设置 → 电池 → 本应用 → 允许后台运行/不优化；允许自启动；关掉该应用的「深度睡眠/智能后台」。改完**重设一条新提醒**再测        |
| 无声无横幅，**通知栏里也没有** | 勿扰/睡眠模式开着                     | 排查表先查这个再查代码——它是三种根因里最便宜的                                                  |
| 无声无横幅，**但通知栏里有**  | 通知发出了，声音/振动被拦                 | 渠道等级（设置 → 应用 → 通知 → 检查该渠道是否「横幅+声音」）；媒体音量≠铃声音量，锁屏状态下听的是**铃声**通道；勿扰「允许例外」配置 |
| 有横幅但没声音           | 同上，且属可用性下降而非失效                | 如实记录偏差；确认 L2 催办链路是否补上了感知                                                  |
| 响了但晚了固定几分钟        | 精确闹钟降级（同第 2 行）或 Doze 维护窗口     | 记录偏差值；`dumpsys alarm` 看注册时是否 `exact`；若每次都晚同样的量，多为降级而非 Doze                |

**与 D-00 / D-01 的分工**（为什么三个都要测）

|         | D-00        | D-05             | D-01       |
| ------- | ----------- | ---------------- | ---------- |
| 屏幕状态    | 亮           | 灭                | 不限         |
| 进程状态    | 活           | 活                | 死          |
| 证明的是    | 页面路径 + 托管成功 | **系统闹钟真的在熄屏时唤醒** | 闹钟独立于进程存活  |
| 失败时第一怀疑 | 通知权限/渠道     | ROM 省电 + 精确闹钟权限  | 闹钟被清（平台行为） |

## 3. A 组 · 无障碍人工六项

> 对应 `03-测试用例清单.md` §四 的 A-01 ~ A-06。
>
> **先说清楚自动化已经做了什么、还差什么**，免得重复劳动或误以为已经做完：
>
> - `a11y.test.cjs`（76 项）锁的是**源码里的数值与属性**：对比度算出来 ≥ 4.5:1、  
>   字号 ≥ 0.8em、点击区 ≥ 44px、`role` / `aria-*` 写在正确的位置上。
> - `a11y-tree.mjs`（75 项）向浏览器索要它**计算后**暴露给辅助技术的**可访问性树**，  
>   核对角色 / 名称 / 状态 / 焦点，并**发真实的键盘与鼠标事件**。
> - 两者合起来**仍然证不了**：读屏念得好不好听、语序顺不顺、焦点环在阳光下看不看得见、  
>   真人能不能只靠键盘走完、以及 WebView 的 ARIA 映射与桌面 Chromium 一不一致。
>
> **所以 A 组不是「重复做一遍自动化」，而是做自动化原理上做不到的那一半。**

### 3.1 读屏准备

**Android · TalkBack**

- 开启：`设置 → 无障碍 → TalkBack → 开启`（部分 ROM 在「辅助功能」下）
- 基本手势（先在系统设置里练 2 分钟再开始）：
  - 单指左右滑动 = 移到下一个 / 上一个元素
  - **双击** = 激活当前聚焦元素
  - 双指滑动 = 滚动页面
- 建议把语速调到**中速以下**再开始，否则你会因为听不清而跳过细节。

**iOS · VoiceOver**

- 开启：`设置 → 辅助功能 → 旁白 → 开启`
- 手势与 TalkBack 基本对应（单指滑动移焦点、双击激活、三指滚动）
- 同样先把语速调慢。

**开工前必做**：在**读屏开启**的状态下走一遍「打开应用」，  
确认读屏能念出应用名与首屏内容。念不出来说明你测的是个空壳，先别往下做。

### A-01 · 读屏跑主流程

**步骤**

1. 开启读屏。
2. 打开应用，用读屏操作完成：「**打开 → 打卡 → 查看记录**」。
3. 过程中**只用手势，不用眼睛去点**（这是本项和 A-05 的区别：A-05 用键盘，本项用读屏）。

**判定（通过条件）**

- [ ] 每个可交互控件都能被念出**有意义的名称**（不是「按钮」、不是「div」、不是「未标注」）
- [ ] 今日页的**多个打卡按钮能被区分**（能听出是在给**哪一剂**打卡，而不是四遍同样的「我已服药」）
- [ ] 焦点**不会卡死**在任何一处（连续滑动能一直走完全部元素并回到开头）
- [ ] 「查看记录」页里，**「漏服」这个状态能被念出来**（不是只有「补服处理」一个按钮）

**必须留证**：整段流程的**录屏带音频**（要能听到读屏在念什么）。静音录屏对本项无效。

**自动化已经锁住的部分**：名称完备性、无通用词名、4 个打卡按钮可区分（`a11y-tree`）、  
Tab 走查不卡死。  
**机器证明不了、只能靠听的部分**：念出来的**语序是否自然**、名称是否**长得让人听不懂**  
（比如「我已服药，二甲双胍缓释片，07:00」在快语速下是否反而更糟）。

**步骤**

2. 切换它，再听一遍。

**判定**

- [ ] 读出的是「**已开启 / 已关闭**」这类状态词，而不是只有一个名字
- [ ] 切换后再次聚焦，读出的状态**与界面显示一致**
- [ ] 8 个开关逐个走一遍，名称都**能说明它管什么**（不是「开关」「switch」）

**留证**：8 个开关逐个的带音频录屏（可合成一段）。

**已覆盖**：8 个开关的角色 / 名称 / `checked` 已由 `a11y-tree` 逐项核对且与数据一致。

### A-03 · 全屏强提醒能被念出

**步骤**

1. 开启读屏。
2. 设置 → 打开「演示加速」→ 点「立即触发一次提醒（演示）」，走到 L3（全屏强提醒）。
3. 听它弹出时发生了什么。

**判定**

- [ ] 弹出时**立刻被播报**（而不是静静地出现、需要用户自己滑过去才发现）
- [ ] 读屏能读到**药名**与操作按钮
- [ ] 焦点**自动进入**对话框内（不会还留在被盖住的时间轴上）
- [ ] 对话框内的两个按钮**都可达**

**已覆盖**：角色 / 名称 / 描述 / `aria-modal` / 焦点已接管 / 两个按钮可达。

### A-04 · 弹层焦点归还

**步骤**

1. 用**键盘或读屏**打开任一弹层（如设置里的某一项）。
2. **路径 A**：按 `Esc` 关闭。
3. 再打开一次，**路径 B**：点遮罩层关闭。
4. 两条路径都观察：关闭后焦点在哪。

**判定**

- [ ] 两条路径关闭后，焦点都回到**打开它的那个按钮**上
- [ ] 不是回到页面顶部，也不是掉到 `document.body`

**留证**：两条路径各一段录屏（能看出焦点环落到哪个控件上）。

**已覆盖**：两条关闭路径（Esc 与点遮罩）都已由真实鼠标/键盘事件实测归还。  
**本项的价值**：确认这份「已覆盖」在**原生 WebView** 里同样成立——  
焦点管理依赖 `focusin` 持续记录 + 可重解析路径（遇带 `id` 的祖先锚定），  
这套机制在 WebView 里的行为需要用真机复核。

### A-05 · 纯键盘操作

**步骤**

1. 关闭读屏（本项验的是键盘可达性，不是语音）。
2. 全程只用 `Tab` / `Shift+Tab` / `Enter` / `Space` / `Esc`，**不碰鼠标和触摸**。
3. 完成：「**开启长者模式 → 打卡一条**」。

**判定**

- [ ] 全程可达，没有需要鼠标才能触发的控件
- [ ] 焦点环**始终可见**（这一条要在**阳光下或老花眼条件下**再看一遍，见 A-06）
- [ ] **无键盘陷阱**（`Tab` 不会卡在某处出不来）
- [ ] 能走到主导航

**留证**：整段流程录屏（镜头要能同时拍到屏幕与按下的键，或直接用屏幕录制+按键悬浮显示）。

真人可能按 60 次、可能误按 `Enter` 提前提交。这类风险只能靠真人观察（A-06）。

### A-06 · 真实老年用户试用

> **A-01 ~ A-05 都是「用机器模拟有障碍的用户」，只有这一项是「真的请用户来」。**  
> 判定对象是**人**，永远无法自动化，也**不能由开发者自己代替**。

**招募**

- 3 ~ 5 位 **55 岁以上**用户
- 最好包含**至少一位老花眼**或**手抖**的用户——他们是本品最典型的极端用户
- 不要招「日常重度用手机」的老人；那样测出来的是「会用手机的人觉得能用」

**伦理底线（请照做）**

- 只观察**操作行为**，不收集任何可识别的健康信息（不记录他们真实在吃什么药）
- 明确告知：这是功能测试，**不提供任何用药建议**
- 用**测试数据**（如「维生素 C」这类无风险占位药），不用他们自己的真实处方
- 征得同意后再录屏；不愿意录屏就只用纸质记录表

**测试脚本（照着念，不要多解释）**

1. 「请您打开这个应用，找到**今天早上那次服药**的位置，给它打个卡。」
2. 「现在请打开**长者模式**，再重复一次刚才的操作。」
3. 「这里有一条显示**没有按时吃**的，您能告诉我它是什么意思吗？」
4. （全程**不提示、不示范**。卡住超过 30 秒再给最小提示，并记录「卡在哪一句」。）

**观察指标（每项都要记数字或原话）**

| 指标                  | 记录方式              |
| ------------------- | ----------------- |
| 能否**自己找到**打卡按钮      | 是 / 否 / 需要提示      |
| 误触次数                | 计数                |
| 是否看懂「**漏服**」这个提示    | 复述原话              |
| 长者模式**是否真的更快**      | 同一任务两种模式的**完成时间** |
| 字体是否够大、按钮是否够大       | 用户原话 + 观察         |
| 焦点环 / 对比度是否在真实光线下可见 | 用户原话              |
| 最卡住的那一步             | 一句话               |

**判定**

- [ ] 大多数用户（≥ 2/3）能**无提示**完成「打卡」
- [ ] 「漏服」提示能被理解（用户复述的意思与设计意图一致）
- [ ] 长者模式在**完成时间**上确实更快，或用户明确表示更省力
- [ ] 没有任何用户因为**看不清 / 点不中**而放弃

**留证**：纸质/电子记录表（每人一份）+ 脱敏后的录屏（可选）。

> 如果这一项的结果是「失败」，**那是本手册最有价值的产出**，不是麻烦。  
> 请把失败原话完整记下来，它比十项绿色对勾更有用。

## 4. C 组 · 家属协同「出网那一跳」

> 对应 `08-家属协同服务端.md` §八 的第一条未闭环项。
>
> **已经验证过什么（别再重复）**：中继端到端 67 项（含 SSE 真实送达、  
> Web Push 加密用**独立实现**解密还原、失败路径）；  
> 应用侧接线 16 项（证明应用**真的把事件交给了中继**）。
>
> **没验证过什么（这才是本项要做的）**：事件从**你自己的中继**出发，  
> 经 **Google FCM / Apple APNs**，到达**家属真机上的一条系统通知**。  
> 这一段没法在本地验证——它需要一个真实的推送服务在中间。

### C-01 · 真实推送服务送达

**前置**

- 一台**公网可达**的服务器 + 一个**可解析域名** + **有效 HTTPS 证书**  
  （没有 HTTPS，`PushManager.subscribe()` 不可用，就只能退回「页面开着才收得到」——  
  那样测的就不是推送通道，而是 SSE 通道）
- 两台设备：一台患者端、一台家属端（**必须是两台真机**，不能用同一台的另一个标签页——  
  同一台机器上本机通知与推送会混在一起，你分不清是哪个通道送到的）
- 中继部署完成，健康检查通过：


```bash
curl https://你的域名/api/health
# 期望：{"ok":true,"service":"mediontime-relay",...,"push":true}
# 若 "push":false → VAPID 密钥没生成成功，先解决这个
```

**反代的那三行不能省**

```nginx
proxy_set_header Connection '';
proxy_buffering off;          # ← 开着它，SSE 会「连上了但永远收不到」
proxy_read_timeout 3600s;
```

**步骤**

1. 患者端配置中继地址（「我的 → 家属协同 → 配置家属服务器」），拿到邀请码。
2. 家属端（第二台设备）打开 `caregiver.html`，填 **服务器地址 + 邀请码**，绑定。
3. **通道一：SSE（页面开着）**
   - 家属端保持页面**开着**
   - 患者端用「演示加速 → 立即触发一次提醒」走到 L4
   - 家属端页面上应**实时**出现这条漏服
4. **通道二：Web Push（页面关掉）**
   - 家属端**关闭页面**（不是切到后台，是关掉），确认订阅已登记
   - 患者端**再触发一次** L4
   - 家属端的**系统通知栏**应出现一条通知
   - **点通知**，应能打开家属端页面
5. 回到患者端，看「家属协同」卡片的「**上次投递**」是否与中继返回一致。

**判定（通过条件）**

- [ ] 通道一：页面开着时**实时**收到（事件从 SSE 长连接上来）
- [ ] 通道二：页面关着时**系统通知**到达 ← **这一条才是本项的核心**
- [ ] 点通知能打开页面（`notificationclick` 生效）
- [ ] 患者端显示的「已送达 N 位」与**家属端真实收到**一致（不是「尝试过 N 位」）
- [ ] 患者端发出的内容**不含药名与剂量**（抓一次中继日志或 `/api/report` 请求体确认）

> **这一条已经在自动化里覆盖**（`browser-check` 11b2 的泄漏探测器：包一层 `window.fetch`  
> 拿真实请求体 + 读中继落库事件，与药箱里逐个药名比对，且跑在**默认配置**上）。  
> 真机上还要看一眼，是因为**原生容器加载的是 `native/www` 同步出来的副本**——  
> 自动化断言过的是 `app/`，而打包产物是从 `app/` 复制过去的。  
> 换句话说：这里验的不是"代码对不对"，而是"**同步有没有真的做过**"。

**必须留证**

- [ ] 两台设备通知的**同框截图**（含时间）
- [ ] 中继日志（含 `/api/report` 的返回：`delivered` / `sseDelivered` / `pushDelivered`）
- [ ] 中继 `/api/health` 输出
- [ ] 一条 `/api/report` 的**原始请求体**（用于证明「不含药名与剂量」）

**常见假通过**

> **① 「家属端页面开着收到了，所以推送通道没问题」** ——  
> 那是 **SSE** 送的，和 Web Push 是两条完全独立的通道。  
> 页面开着时 SSE 会先到，你甚至不会注意到推送成没成功。  
> **必须把页面关掉再测一遍**——只测通道一的人，会以为两条都通了。
>
> **② 「患者端显示「已送达 1 位家属」，所以成功了」** ——  
> 这个数字来自中继返回的 `delivered`。如果家属端并没有真的出现通知，  
> 说明问题出在中继**之后**（真实的 FCM/APNs 那一跳）。  
> 中继会把 `pushErrors` 一起返回（如「推送端点返回 500」），**去看它**。  
> 本项目历史上最贵的一条谎就是「把『尝试过』说成『已通知』」——  
> 现在这句话在应用里已经被断言锁死了（未配置时中继事件数必须为 0），  
> 但**中继之后的失败仍然要靠这一项真机验证**。
>
> **③ iOS 上「订阅成功了但收不到」** ——  
> Safari 要求 PWA **先「添加到主屏幕」**&#x624D;可能有 Web Push。  
> 这一步**从未在真机验证过**。如果在 iOS 上做本项，请先完成「添加到主屏幕」，  
> 并把它作为**前置步骤**记录在案，而不是当成失败。
>
> **④ 用同一台设备的两个标签页测** —— 本机通知与推送混在一起，无法归因。  
> 必须两台设备。

## 5. B 组 · 真机功耗实测

> 对应 `06-部署与上架指南.md` §六 提到的「本轮未做真机功耗实测」。
>
> **先说一句可能让人不想测的话**：原生下真正的耗电大头  
> **不是**应用内的提醒轮询，而是**系统闹钟本身与常驻通知**。  
> 轮询优化（自适应唤醒：临近事件 30 秒 / 空闲 5 分钟上限）主要影响  
> 应用在前台或后台存活时的开销。所以这一项测出来如果「数字不好看」，  
> 先分清是**谁的账**，再决定要不要改代码。

### B-01 · 唤醒次数与静置功耗

**工具**

- Android：`adb bugreport` + **Battery Historian**
- 或最朴素的对照法：系统设置里的「电池 → 应用耗电」（精度低，但零门槛）

**步骤**

1. **建立基线**：充满电，拔充电器，记录起始电量与时间；  
   让手机**完全静置**（关屏、不连网也行，但要和你后面的测试条件一致）**4 小时**。
2. 导出报告：
   ```bash
   adb bugreport ~/bugreport-baseline.zip
   ```
3. **装应用后再测一次**：同样充满、同样静置 4 小时，再导一份报告。
4. 两份报告一起丢进 Battery Historian 对比。

**判定**

- [ ] 两份报告的**唤醒次数（Wakeups）差异**与「应用内算出的唤醒次数」**同量级**
- [ ] 没有出现「每小时几十次」的异常唤醒风暴（那是轮询或闹钟泄漏的信号）
- [ ] 待机耗电的差异在你可接受的范围内（这一条没有绝对阈值，看你的产品定位）

**必须留证**

- [ ] 两份 `bugreport`（或两张系统电池页截图，注明时间段）
- [ ] 应用内算出的唤醒次数（设置 → 提醒可靠性详情里的相关说明）
- [ ] 结论：**耗电主要来自哪一项**

**常见假通过**

> **① 「我只测了装应用之后，看到耗电不高」** ——  
> 没有基线就没有对照。同一台手机在不同日子里因为信号、后台更新、  
> 系统升级，耗电可以差出一倍。**必须两份报告对比。**
>
> **② 「唤醒次数高，所以轮询有 bug」** ——  
> 先看唤醒的**归因**。如果大头是 `AlarmManager`（系统闹钟）  
> 或常驻通知，那是**设计使然**，不是 bug——提醒要准，就得被唤醒。  
> 这项的意义是**分清账**，不是把数字压到零。

## 7. 与自动化测试的边界对照

**这张表是本文档存在的原因。**

| 可访问性树里的角色 / 名称 / 状态 / 焦点归属          | `a11y-tree.mjs`（75 项，桌面 Chromium）       | 读屏**实际念出来**的语序与语速；WebView 的 ARIA 映射是否一致 |

| 中继能正确加密、签名、扇出、处理失败                  | `server/tests`（67 项）                    | 同上；以及公网 + HTTPS 下的真实链路                  |
| 系统闹钟的**注册计划**与权限补丁正确                | `platform.test.cjs` + `native.test.mjs` | 系统**真的到点时把它唤醒了**                        |

## 8. 附录

### A. adb 速查

```bash
# 设备与安装
adb devices
adb install -r <path/to/app-debug.apk>
adb shell dumpsys package cn.mediontime.app | grep -i versionName

# 杀死应用（D-01 用这个——不会清除已注册闹钟）
adb shell am kill cn.mediontime.app
adb shell ps -A | grep mediontime            # 期望：无输出

# ⚠️ force-stop：**会连带移除全部已注册闹钟**（Android 平台行为，任何应用皆然）。
# 只在你想验证「平台边界」时使用，不要用它做 D-01 的测试手段：
adb shell am force-stop cn.mediontime.app

# 系统侧是否排着闹钟
adb shell dumpsys alarm | grep -i cn.mediontime

# 精确闹钟开关状态（部分 ROM 需要 root）
adb shell appops get cn.mediontime.app SCHEDULE_EXACT_ALARM

# Doze（打盹）
adb shell dumpsys deviceidle force-idle      # 进入
adb shell dumpsys deviceidle get deep        # 查状态
adb shell dumpsys deviceidle unforce         # 退出
adb shell dumpsys battery reset              # 恢复电池状态

# 日志（tag 名随插件版本变化，用 grep 更稳）
adb logcat -v time | grep -iE "mediontime|Notification|LocalNotif|Alarm"

# 重启
adb shell reboot

# 功耗
adb bugreport ~/bugreport-<场景>.zip
```

> 上表里只有 `force-stop` / `reboot` / `deviceidle` 系列 / `bugreport` 是官方文档明确给出的用法。  
> `appops get` 与 `dumpsys alarm` 的输出格式**随 Android 版本与厂商 ROM 变化**，  
> 请以你实际看到的内容为准——如果某条命令返回空或报错，**先用 `--help` 或换等价写法确认**，  
> 不要把它当成「缺陷已复现」。

### B. 证据命名规范

统一用 `<用例号>_<设备>_<日期>_<类型>.<扩展名>`，例如：

```
D-01_xiaomi14_20261011_screenrecord.mp4
D-01_xiaomi14_20261011_dumpsys-alarm.txt
A-03_pixel8_20261011_readback.m4a
C-01_two-devices_20261011_screenshot.png
```

要求：

- **时间要进文件名**（同一项可能要跑多次，靠序号区分）
- 录屏类证据**必须带系统时间**（录屏时把状态栏带进去）；读屏类证据**必须带音频**
- **原始文件不要裁剪**（裁过的证据会被下一个人怀疑，就像我们怀疑过的那些截图一样）

### C. 「提醒没响」的三类根因分诊

**遇到「没响」时，先别改代码，先归因。** 这三类的修法完全不同：

| 类型              | 现象                            | 怎么确认                        | 通常的根因                                    |
| --------------- | ----------------------------- | --------------------------- | ---------------------------------------- |
| **① 根本没注册**     | 到点毫无动静，且 `dumpsys alarm` 里也没有 | `dumpsys alarm \| grep` 无输出 | 权限没给 / 渠道没建 / `boot()` 没同步 / 跑在 Web 平台   |
| **② 注册了但被系统推迟** | 晚了，但最终还是响了                    | `dumpsys alarm` 里能看到，时间戳偏后  | 精确闹钟未授权（D-03）/ Doze 维护窗口（D-04）/ ROM 后台限制 |
| **③ 触发了但用户没感知** | 系统里记录到了，人也说「没听见」              | 通知栏历史里有该通知                  | 渠道重要性被降（只能降不能升）/ 被系统静音 / 勿扰模式 / 通知被折叠    |

> 三类里**只有 ② 和「准时」有关，①和 ③ 都跟准时无关**。  
> 把 ③ 当成 ① 去查闹钟，是这个项目最容易浪费半天的地方。

### D. 本手册的维护约定

- 新增用例**往下续编号**，不复用、不换义；编号一旦写进记录表就固定下来。
- 每一项都必须有「**常见假通过**」一栏。没有这一栏的用例，说明还没想清楚它会被怎么骗过。
- 当某项的结论从「未通过」变成「通过」时，**同步更新** `03` §六 的测试结论表  
  与 `06` §八 的未闭环表——**文档里留着一个已经修好的「未闭环」，也是一种谎言**。
- 本手册**不记录结论**。结论在 §6 的记录表里。手册本身永远保持「待执行」状态。
