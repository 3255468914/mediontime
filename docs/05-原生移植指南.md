# 05 · 原生移植指南

> 本文件回答一个问题：**要让"提醒必达"真正成立，还需要做什么。**
> 前四份文档把需求、数据、测试写清楚了，但没有解决 Web 平台的硬限制。

---

## 1. 为什么必须移植

产品的 11 条验收标准（DoD）里，第 2、3 条是：

- 第 2 条：手机重启后，提醒仍能准时触发
- 第 3 条：应用被系统清理后，提醒仍能准时触发

这两条验证的是整份文档反复强调的生命线——"提醒必达"。而浏览器在页面关闭后
**不执行 JavaScript**，这是平台层面的约束，不是实现缺陷，也不是优化能绕过的。

> 结论：在纯 Web 技术路线上，这两条**不可能通过**。
> 继续在 PWA 上堆 P2 功能（统计、家属协同）价值有限，因为核心价值不成立。

因此 P2 的首要任务是换投递通道，而不是加功能。

## 2. 路线选择：为什么是 Capacitor 而不是重写 Flutter

| 方案 | 工作量 | 提醒必达 | 风险 |
|---|---|---|---|
| 继续 PWA | 0 | ✗ | 核心价值不成立 |
| **Capacitor 包壳** | 低（业务代码零改动） | ✓ | 界面仍是 WebView 渲染，极端低端机性能一般 |
| 重写 Flutter | 高（UI 全部重做，1000+ 行） | ✓ | 工期长，且收益不在 UI |

选 Capacitor 的依据是**代码结构本身**：`app/js/scheduler.js` 与 `app/js/platform.js`
是平台无关的纯函数模块，迁移是"原样复用"而不是"翻译重写"。

```
┌─────────────────────────────────────────────┐
│  app/js/scheduler.js   排程、状态判定、补救决策   │  ← 纯函数，115 项测试覆盖
│  app/js/platform.js    投递抽象层               │  ← 纯函数，152 项测试覆盖
└─────────────────────────────────────────────┘
              ↓ 同一份代码
   ┌──────────────┐        ┌──────────────────┐
   │ WebPlatform  │        │ NativePlatform   │
   │ 页面内定时器   │        │ 系统级闹钟        │
   └──────────────┘        └──────────────────┘
     应用打开才响              应用被杀 / 重启也响
```

上层只调用 `Platform.sync(jobs)`，不需要知道自己是跑在浏览器还是原生容器里。
这就是为什么平台抽象层要在移植之前先做——**先分层，再换实现**。

## 5. 平台差异清单（实现时踩过的真实约束）

### 5.1 Android

**配额**：无硬上限，但注册过多会被系统限流 → 代码取 512，并预留 4 条安全余量。

**精确闹钟是独立开关，不是权限**
Android 12+ 用户可在系统设置里单独关闭。官方文档明确：一旦关闭，
**系统会重启应用并删除所有已排的精确闹钟**。
→ 应用启动后必须重新同步（`boot()` 已处理），并用 `checkExactNotificationSetting()`
查真实状态、用 `changeExactNotificationSetting()` 引导用户去开。

**不要声明 `USE_EXACT_ALARM`**
Google Play 限定给"闹钟/日历类应用"，用药提醒声明会被拒审。
用 `SCHEDULE_EXACT_ALARM` + 用户授权替代。补丁脚本里有注释说明。

**Doze 模式的 9 分钟节流**
官方文档：带 `allowWhileIdle` 的提醒"每个应用每 9 分钟只能触发一次"。
而 L1→L2 间隔是 5 分钟——若两级都加豁免，L2 会吃掉当天后续提醒的额度。
→ 只给 L1 加豁免，L2 允许被推迟到下一个维护窗口。这个取舍写进了
`platform.js` 的 `allowWhileIdleFor()` 与对应测试。

**通知渠道的重要性等级不可逆**
渠道一经创建，重要性只能降不能升（除非卸载重装）。默认渠道是 DEFAULT，
只会在通知栏静静出现、不横幅不响铃——对用药提醒等于没提醒。
→ 显式建 `med-normal`(IMPORTANCE_HIGH) 与 `med-alert`(IMPORTANCE_MAX)，
且在注册提醒**之前**建好。渠道建成时用户还没开始用，正确性影响最小。

### 5.2 iOS

**硬上限 64 条待触发本地通知**
→ `planNativeBatch` 按配额截断，只注册最近的一批，其余标记 `deferred`
并在下次前台刷新时滚动补齐。iOS 上有效额度取 60（预留 4 条余量）。
用户侧需要知道这个约束，所以设置页在溢出时明确提示"请保持每周至少打开一次应用"。

**重启无需开机广播**：iOS 由系统持久化待触发请求，`survivesReboot` 取
"由系统持久化"而非 false。

**静音模式下响铃需要 Critical Alerts 权限**，需向 Apple 单独申请，且仅限健康类
应用。当前未申请，默认行为是静音模式下不响。这是已知限制。

### 5.3 两端共同的

**通知 ID 必须是 int32**（Android 要求 −2147483648 ~ 2147483647）。
→ `toNativeId()` 用 FNV-1a 哈希映射到 `[1, 2^31−1]`，并做线性探测避免同批次
内 ID 冲突互相覆盖。同一个"提醒 + 级别"永远映射到同一个 ID，保证幂等。

## 6. 尚未实现的两项能力（附补齐方案）

### 6.1 L3 后台全屏强提醒

**现状**：全屏强提醒只在应用处于前台时生效。

**补齐方案**：Android 前台服务（`startForeground` + 常驻通知）配合
`USE_FULL_SCREEN_INTENT`。可行，但代价是状态栏常驻一条通知。
建议做法是"仅在提醒窗口期内启动前台服务"（例如服药时间前后 30 分钟），
其余时间退出，避免长期占用。

**要不要做**：建议先做用户调研。对慢病老年用户，常驻通知可能反而造成困扰；
而 L1 通知 + 声音震动 + L2 催办通常已经够用。

### 6.2 L4 通知家属

**现状**：**P8 已实现跨设备投递**，见 [`08-家属协同服务端.md`](./08-家属协同服务端.md)。

实现方式与下面这份"补齐方案"基本一致，但有一个刻意的差异：
**没有引入账号体系，也没有绑定到第三方云推送**，而是做成一个
**你可以自己部署的零依赖中继**（`server/`）。家属用邀请码绑定，
事件只包含"某条提醒未确认"（**不含药名与剂量**，最小必要原则），
投递走 SSE（页面打开时）与 Web Push（页面关闭时）。

**原生容器接入时需要补的**（本机无法验证，需真机）：
1. 原生侧的设备推送令牌注册（FCM / APNs）——Web Push 在 iOS 上另有限制
   （Safari 要求先"添加到主屏幕"），原生容器应直接走 APNs 而非 Web Push
2. 中继的账号与令牌体系（当前是邀请码 + 随机令牌，够用但无吊销机制）
3. 中继的限流与 CORS 收紧（公网暴露前必须做，见 `docs/08` §6）

> 已实现并可验证的部分本机已全部验证：中继端到端 69 项、
> 应用侧接线 16 项（`browser-check` §11）。
> **未验证的是"出网那一跳"**——即真正经 Google/Apple 推送服务送达。
> 搬运到原生工程时，最需要重新确认的就是这一跳。

## 7. 移植前的检查清单

```bash
# 1) 核心逻辑回归（不需要 SDK）
cd app   && node tests/scheduler.test.cjs   # 115 项
             node tests/platform.test.cjs    # 152 项
             node tests/smoke.test.cjs       # 139 项
             node tests/pwa.test.cjs         #  37 项（Service Worker）
             node tests/a11y.test.cjs        #  76 项（无障碍与长者模式）

# 2) 原生脚本回归（不需要 SDK）
cd native && npm test                        # 131 项

# 3) 真实浏览器回归（需要起静态服务器）
cd app && python -m http.server 8788 --bind 127.0.0.1
         node tests/browser-check.mjs --port 8788   #138 项（含 SW 真实安装、到点唤醒、漏服可见性、家属协同接线、**药名泄漏探测器**、家属端页面本身）
         node tests/a11y-tree.mjs --port 8788       # 75 项（真实可访问性树：角色/名称/状态/焦点）
         node tools/ui-shots.mjs --port 8788        # 43 项（12 个关键页面渲染断言 + UI 稿 + 清单自校验）
```

合计 **993 项**，移植前应全绿。其中 `a11y.test.cjs` 尤其要在移植前跑：
原生容器沿用同一份 `css/style.css`，字号与对比度的改动会**一并带进安装包**。

`a11y-tree.mjs` 在移植后同样值得重跑：它读的是 WebView **计算出来**的可访问性节点，
而 Android WebView / iOS WKWebView 对 ARIA 的映射与桌面 Chromium **并不完全一致**，
是移植后最容易悄悄退化的一层。

`ui-shots.mjs` 在移植后尤其值得重跑一次：原生 WebView 的字体渲染、
安全区（safe-area）与浏览器不同，容易把长文案挤坏——
出图后与 `docs/07-关键页面UI稿.md` 里的浏览器版逐页对照即可发现。

装好 Android SDK 后：

```bash
cd native
npm install                    # 装 Capacitor 依赖（本机实测：npm 官方源不通时改用
                               #   npm install --registry=https://registry.npmmirror.com）
npm run android:add            # 生成 native/android/
                               #   ⚠️ 本仓库**已经生成过**（android/ 随仓库提交）。
                               #   若该目录已存在，跳过这一步——重复执行会报 "already exists"。
npm run patch:android && npm run patch:check
npm run sync && npm run open:android
```

> **生成了工程 ≠ 能编译。** 本机已完成 `android:add` + 6 条权限补丁 + `www` 同步，
> 并核实过权限齐备、安装包资源逐字节一致（见 `docs/04` §4.9）。
> 剩下的只有 **Gradle 编译**这一跳，它需要 **JDK 17+**（本机是 JDK 1.8）
> 与 **Android SDK**（`compileSdk 36 / minSdk 24`，Gradle 8.14.3）。

真机上必须实测的四件事：

> **具体怎么做，见 [`09-真机验收手册.md`](./09-真机验收手册.md)。**
> 那里把下面 4 件事写成了逐步骤可执行的形式（含精确的 adb 命令、
> 必须留什么证据、每项「最容易骗过自己」的假通过、以及一张失败分诊表），
> 并补了一件本节没写、但**不做就会让下面 4 项结论全部不可信**的前置：
> **D-00 基线** —— 先证明「应用开着时能准点响」，再去测「被杀 / 重启后还能响」。
> 否则 D-01 失败时你分不清是「被杀导致」还是「从来就没响过」。

1. 设一条 3 分钟后的提醒 → 划掉应用 → 是否按时响
2. 同上 → 重启手机 → 是否按时响
3. 关掉「设置 → 应用 → 药准时 → 闹钟和提醒」→ 是否降级为不精确提醒、
   设置页是否如实报出「精确闹钟授权：未授权」
4. 开省电模式 / 让手机静置进入 Doze → L1 是否仍能准时触发

第 3、4 项最容易被跳过，而它们恰恰是这个产品最容易"看起来正常但实际不响"的地方。

装好 SDK 后建议**再补第 5 项**：

5. 打开 TalkBack（Android）跑一遍「打开 → 打卡 → 查看记录」主流程

`app/tests/a11y.test.cjs`（源码级）与 `app/tests/a11y-tree.mjs`（浏览器计算后的 AX 树）
都只能证明**属性写对了**与**桌面 Chromium 把属性算对了**，
**证明不了读屏实际怎么念、焦点实际怎么走**，也证明不了 WebView 的映射一致。
这一条只能靠真人和真机。
