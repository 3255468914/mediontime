# 10 · 优化与加固评估

> 生成日期：2026-10-11　｜　触发：真机验收期间「家属协同可用，但应用在后台/熄屏收不到通知」
>
> 这份文档回答一个问题：**这个程序还有哪些能优化的地方**。
> 只列**有依据**的（有代码位置或真机实测支撑），每条写明：现状 → 影响 → 建议 → 成本。
> 区分「必须做 / 值得做 / **不建议做**」——最后一类同样重要，
> 因为最贵的不是漏了一个优化，而是为了"看起来更专业"引入一个不必要的复杂度。

---

## 一、提醒送达可靠性（最高优先级：它决定产品是否成立）

### 1.1 【本轮已修】回到前台不重新注册系统闹钟

- **现状**（修前）：`app.js` 的 `visibilitychange` 只调用 `RE.reschedule()`——
  它只重排**页面内**引擎。而系统会在后台清掉闹钟（重启、权限变更、
  长时间闲置、国产 ROM 深度管控），页面内引擎对这件事一无所知。
- **影响**：典型沉默失败——**界面一切正常，到点什么都不响**。
  这类缺陷不报错、不崩溃，只能靠真机到点守候才能发现。
- **建议**：回到前台同时 `scheduleSync()`，把系统闹钟重新对齐一次。
- **状态**：✅ 已修 + 源码锁（`smoke.test.cjs`：断言 `visibilitychange` 块内既有
  `RE.reschedule()` 也有 `scheduleSync()`）。

### 1.2 【本轮已修】「提醒不可靠」只有点进「我的」才能看到

- **现状**（修前）：通知权限被关、精确闹钟未授权、注册失败、托管 0 条——
  这些状态只在「我的 → 提醒可靠性」卡片里出现。
- **影响**：长者几乎不会进这一页。于是"提醒已经不可能响了"在首页**完全隐形**，
  用户会一直以为应用在正常工作。
- **建议**：抽一个 `reliabilityIssue()` 判定 + 首页顶部红色横幅，附「去处理」入口。
  横幅只覆盖**会让提醒失效**的红线；可靠性卡片继续展示「超出托管上限」这类非致命提示。
- **状态**：✅ 已修 + 源码锁（断言首页渲染里含 `reliabilityBanner()`，且三种状态都被判定覆盖）。

### 1.3 【本轮已修】「通知家属」依赖患者手机存活

- **现状**（修后）：患者端在排程变化时把每剂 L4 时刻（直接取
  `Scheduler.buildEscalation()` 算出的结果，**不在服务端重复实现升级链**）
  全量上报给中继（`POST /api/notify-schedule`，对账语义：删药/改时间/关通道
  自动跟上）；患者确认/跳过/补录/漏服结算时上报撤销（`/api/notify-cancel`）；
  中继到点仍未收到撤销 → 推送给家属。患者端实时上报 L4（手机活着）时
  中继自动撤销对应待办，家属不会收到重复通知。
- **失败方向是安全的**：患者手机死机/关机/被冻结时，家属**照样收到**（这正是期望行为）。
- **隐私边界**：待办与事件仍只有内部随机 id 与时刻，**没有药名**（白名单构造器
  新增 `reminderId`，它是随机生成的编号，与药名的映射只存在患者手机本地）。
  隐私政策（`showPrivacy`）、家属协同弹层、docs/08 §4.1 三处已同步改写。
- **状态**：✅ 已修 + 测试锁（relay 第 9 组 18 项：上报/撤销/到点推送/防重复/
  持久化；smoke 11 项源码锁；家属协同卡片显示「计时待办：中继托管 N 条」）。
- **如实边界**：撤销依赖患者端此刻能连上中继；断网时的撤销发不出去，
  中继会照推一次「未收到确认」，家属打电话核实即可——这比在服药流程里
  插一条报错更安全。中继到点只推一次（推完即删）。

### 1.4 【本轮已修】L2 之后到用户打开应用之前是静默的

- **现状**（修后）：L3（+15 分钟强催办）已纳入系统托管（`levels: [1,2,3]`），
  走「用药催办」渠道（与 L2 同渠道，IMPORTANCE_MAX）。L3 不带
  `allowWhileIdle`，Doze 下允许推迟到维护窗口——+15 分钟的间隔本来就在
  9 分钟节流窗之外，不挤占 L1 的准时额度。
- **状态**：✅ 已修 + 测试锁（platform 第 2 组改判 + 第 20 组 7 项；smoke 源码锁）。
- **注意**：托管批次每剂多一条通知（2→3），远未来提醒被配额推迟的概率
  略有上升——`planNativeBatch` 的截断与「推迟 N 条」如实提示已覆盖。

### 1.5 【待办 · 真机】尚未留证的部分

- D-01 ~ D-05（真机提醒五问）、A-01 ~ A-06（读屏器人工）、B-01（功耗实测）、
  C-01（公网 + HTTPS 下的 Web Push，局域网 SSE 已通）。
- 特别提醒：**卸载重装会重置全部系统授权**（通知权限、精确闹钟、ROM 自启动/后台运行）——
  2026-10-11 真机上"后台/熄屏不响"的首要怀疑就是它。
  建议在安装说明与上架文案里写明"重装后请重新授权"。

## 二、省电与性能

| 项 | 现状 | 建议 | 成本 |
|---|---|---|---|
| 唤醒策略 | ✅ 自适应唤醒（`nextDelay`，已无 `setInterval` 每秒轮询） | 保持；源码锁已防止改回 | — |
| 闹钟重建 | 每次数据变化后**全量重建**系统闹钟（按托管上限截断） | 增量 diff（只取消/新增变化条目）。仅在**上千条提醒**时才明显 | 中 |
| 前端渲染 | 页面级整体重渲染，列表规模在百级 | 暂不优化（当前规模下无实测问题） | — |
| 保活 | 未使用前台服务 | **不建议做**（见下） | — |

> **不建议做**：为"后台一定活着"加前台服务/常驻通知。它耗电、被国产 ROM 优先清理，
> 且给长者增加一个看不懂的常驻通知。正确解法是 **1.3**（把计时搬到服务端），
> 而不是让手机一直醒着。

## 五、工程与交付

1. ✅ 993 项自动化断言、真机验收手册、全程国内镜像构建链、可安装 APK。
2. 【值得做】**把 APK 产物核验固化成一条命令**：本轮人工做了
   `aapt dump xmltree` 查权限、`unzip -p` 查 `capacitor.config.json`，
   这类核验每次发版都要做，应写成脚本并按断言输出。
3. 【值得做】三套浏览器测试依赖**外部**静态服务器（本轮与用户的服务共用 8788 端口），
   忘了起服务就会得到"全红"，容易被误读为代码问题。
   建议测试自带 `spawn` 一个静态服务并在结束时回收。
4. 【待办】上架：开发者账号、隐私政策、应用商店类目合规（用药提醒类目审查较严）。
5. 【已记录 · 环境坑】**在某些受限环境里 `npx cap sync android` 会删掉自己的生成文件而不再重建**：
   `android/capacitor-cordova-android-plugins/` 下的 `build.gradle` 与
   `cordova.variables.gradle` 被删除后，下一次 Gradle 构建直接失败
   （报 `Could not read script ... cordova.variables.gradle as it does not exist`）。
   恢复方法（两者内容都是模板，可从 `node_modules/@capacitor/cli/assets/`
   的 `capacitor-cordova-android-plugins.tar.gz` 与 CLI 源码 `android/update.js`
   中的生成模板还原；`cdvMinSdkVersion` 取本项目 `android/variables.gradle` 的值）。
   **更稳的做法**：同步 web 资产后，改 web 代码再出海时优先重跑
   `npm run sync`（本项目脚本）并立即构建验证，而不要假定 `cap sync` 一定完整成功。

## 六、优先级建议

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P0** | ✅ 1.1 前台重挂系统闹钟（10-11） | 沉默失败，直接导致"到点不响" |
| **P0** | ✅ 1.2 首页可靠性横幅（10-11） | 让不可靠**可见** |
| **P0** | ✅ 1.3 L4 交给中继计时（10-12） | 家属协同在最需要时恰好失效 |
| **P1** | ✅ 1.4 L3 纳入系统托管（10-12） | 催办链到 L2 之后不再静默 |
| P1 | 三·邀请码限流 / D 组留证 | 成本低、收益直接 |
| P2 | 二·增量同步 / 五·APK 核验脚本 / 五·测试自带服务 | 工程质量，不影响当前功能 |
| **不做** | 前台服务保活、账号体系、云端病历同步 | 与本产品的隐私承诺与目标用户相冲突 |

## 七、诚实边界

- 本评估的每一条都对应到具体代码位置或实测现象；**没有实测支撑的推测已标注为"待真机"**。
- 二·1 的"回到前台重挂闹钟"只保证**打开应用后**闹钟恢复；
  开机到首次打开应用之间，系统闹钟由 `RECEIVE_BOOT_COMPLETED` 与插件行为决定（D-02 待实测）。
- 1.3 若落地，中继会知道"某位患者在某时刻有一条提醒"，这是隐私上**新增**的一类信息，
  必须同步更新隐私政策与家属协同说明页——不能只在代码里做。
