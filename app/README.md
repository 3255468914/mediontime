# 药准时 · 用药提醒 App（MVP）

面向长期服药人群及其家属的用药提醒与依从性管理工具。技术形态是
「零依赖 PWA 内核 + Capacitor 原生容器 + 可选自建中继」。

> 中继服务端是为「家属能收到漏服通知」增加的可选组件，
> 见 `../docs/08-家属协同服务端.md`。**它是可选的**：不配置时应用一个请求都不发，
> 行为与没有家属协同完全一致。

---

## 一、快速开始

### 方式 1：直接打开（最快）

双击 `index.html` 即可在浏览器中使用。核心功能（排程、打卡、记录、统计）完整可用。

> 注意：`file://` 协议下浏览器会禁用系统通知权限申请与 Service Worker，**提醒到点不会弹系统通知**（应用内的全屏强提醒仍可正常工作）。

### 方式 2：本地服务器（推荐，可体验完整能力）

```bash
cd app
python -m http.server 8777
# 然后浏览器打开 http://127.0.0.1:8777/index.html
```

`http://` 下可申请系统通知权限、可注册 Service Worker 离线缓存。

### 方式 3：装到手机

用手机浏览器打开方式 2 的地址（需同一局域网），菜单里选「添加到主屏幕」，即可作为 PWA 独立运行。

### 调试参数

| 参数 | 作用 |
|---|---|
| `?auto=1` | 跳过免责声明引导页，直接进入主界面 |
| `?page=today\|meds\|log\|stats\|me\|plan` | 直接打开指定页面 |
| `?simTz=UTC-11` | 模拟「从该时区切换过来」，用于走查时区二选一流程 |

合计 **993 项**（上面这段是 `app/` 内的 9 套；另有 `../native/tests/native.test.mjs`
的 131 项原生工程脚本测试，在 `native/` 目录下跑，计入总数）。
前五套是零依赖的纯 Node 脚本，不需要 `npm install`。
第 6 套用 Chrome DevTools Protocol 驱动 Edge/Chrome 无头模式，能验证
`app.js` 与 `platform.js` 的真实启动链路、**Service Worker 的真实安装状态**、
**提醒到点是否真的被唤醒**、**漏服状态是否真的写出来了**、
**家属协同的接线是否真的接上了**（第 11 组）、
以及**家属端页面本身**（第 12 组，此前那 35 项测的是测试代码里自写的 SSE 客户端，
而不是 `caregiver.html` 这个真正给人看的页面）。
第 7 套通过 CDP 的 `Accessibility` 域读取浏览器**计算后**的无障碍节点，
验证"源码里写的 aria"确实变成了"读屏器读到的东西"——控件有没有名字、
开关的 checked 有没有跟着翻转、模态对话框有没有真的接管焦点。
第 8 套既产出交付物（`../docs/ui/` 12 张 UI 稿），也断言这些页面真的渲染出来了；
并**反过来读一遍磁盘**核对清单里的尺寸与 sha256（"用来核对别人的东西，自己先得被核对"）。
第 9 套起一个真实中继服务，让一位真实家属端连上 SSE，
断言**事件真的到达了那条长连接**；Web Push 部分用一个本地模拟推送服务
**独立实现 RFC 8291 解密**，把载荷还原回原文。

> `a11y.test.cjs` 是**回归锁，不是合规证书**。它锁住的是对比度、字号、点击区、
> 语义这些参数别被后人"顺手调回原样"，而不是"已通过无障碍认证"。
> 语义与焦点顺序的实际效果，只有用读屏软件真跑一遍才算数——**本轮没有做这件事**。

> `a11y-tree.mjs` 与 `a11y.test.cjs` 是两层，缺一不可：
> 前者证明"源码里写了正确的 aria"，后者证明"浏览器真的把它算对了"。
> 分开写正是为了让"声明"和"事实"能各自被核对——
> 本项目最防的就是这两者不一致（见 `../docs/04` §4.7）。

> `ui-shots.mjs` 为什么把"截图"和"断言"写在一起：如果只截图不断言，
> 一个白屏页面也会被安静地存成 PNG，然后贴进文档显得"有图有真相"。
> 这两件事必须是同一件——**「页面渲染出来了」和「这张图被生成」是一个结论的两个侧面**。

## 五、关键实现说明

### 5.1 提醒等级「按时间反推」而非定时器累加

`reminder.js` 每秒 tick 一次，但对每条提醒都是**根据当前时间重新计算它应该处于哪个等级**，而不是依赖定时器逐级累加。

好处：刷新页面、切换后台再回来、甚至重启浏览器后，提醒都会落在正确的阶段，不会漏级、不会重放、不会刷屏。

### 5.2 不回填历史（BR-01）

`generateSchedule(from: now)` 只生成当前时刻之后的提醒。当天已经过去的时间点不会被生成，避免一打开应用就被过期提醒刷屏。

代价是「今天早上的那一剂」可能没有提醒对象 —— 这由 `Store.reconcileMissed()` 在启动时结算：超过漏服窗口且完全无记录的，补记为漏服事实。今日页则改为**按计划时间点渲染**，因此任何情况下都不会漏项。

### 5.3 幂等性

以下操作在测试中均验证了幂等：

- 重复生成排程 → 不产生重复提醒
- 重复打卡 → 返回同一条记录，不新增
- 重复标记漏服 → 不产生重复记录
- 同一等级重复触发 → 不重复弹通知

### 5.4 演示加速

「我的 → 演示加速」开启后，升级间隔被压缩 50 倍：
`+5 分钟 → 约 6 秒`、`+15 分钟 → 约 18 秒`、`+30 分钟 → 约 36 秒`。

配合「立即触发一次提醒」按钮，可以在 1 分钟内完整观察 L1→L5 全链路。

### 5.5 自适应唤醒（省电）

早先 `reminder.js` 用 `setInterval(tick, 1000)`：**每秒醒一次、每次遍历全部提醒**。
一条 90 天 × 每日 3 次的计划就是 270 条，多药并用上千条 ——
于是应用即使闲置、主人正在睡觉，每秒也在做几百次 `Date` 解析。

现在改成**自适应唤醒**：算出「下一个该做事的时刻」，睡到那一刻再醒。

| 场景 | 旧实现 | 现在 |
|---|---|---|
| 一条提醒在 3 小时后 | 10800 次唤醒 | **54 次** |
| 完全空闲（无待触发提醒） | 3600 次/小时 | **12 次/小时** |
| 提醒在 20 秒后 | 20 次 | **1 次** |
| 到点是否迟到 | — | **不迟到** |

**为什么敢把轮询拉长**：本引擎的等级是「按当前时间反推」的，
醒得晚了不会漏级、不会重放，只会把该做的补上 ——
也就是说**正确性不依赖醒得多勤**。这正是能用自适应唤醒的前提，
也正是第一版那个设计决策在后续继续产生收益。

另设兜底上限（临近事件 30 秒 / 空闲 5 分钟），防止用户改系统时间、
时钟跳变、休眠恢复导致睡过头。回到前台时用 `reschedule()` 立即对齐真实时间。

> 所有会改变排程的入口（增改药品、归档、时区二选一、改演示加速、打卡、跳过、补服、
> 补录、推迟、演示触发）都会显式调用 `RE.reschedule()`，
> 否则会出现「新加的药 2 分钟后该吃，却要等兜底上限才响应」。

## 六、已知限制（重要）

| 限制 | 说明 | 解决路径 |
|---|---|---|
| **浏览器后台提醒** | 页面关闭后浏览器不再执行 JS，无法到点弹提醒。这是 Web 平台的硬限制。 | **已解决**：`native/` 原生容器把投递改成系统级闹钟，业务代码零改动。见 `../native/README.md` |
| L3 后台全屏强提醒 | 全屏强提醒仅在应用处于前台时生效。 | 需 Android 前台服务（常驻通知），方案见 `../docs/05-原生移植指南.md` §6.1 |
| 家属通知 | **已是真实跨设备投递**（F-28，自建中继 + SSE + Web Push）。 | 需要你自己部署 `server/`；跨网络还需公网地址 + HTTPS。**经真实 FCM/APNs 的那一跳未验证**，公网部署前须按 `../docs/08-家属协同服务端.md` §六收紧（限流、CORS、令牌吊销）。 |
| iOS 静音模式响铃 | 静音模式下不会响。 | 需向 Apple 单独申请 Critical Alerts 权限（仅限健康类应用） |
| 通知权限 | `file://` 下无法申请通知权限，必须走 `http://` 或 `https://`。 | 原生应用无此限制。 |
| Service Worker 仅在顶层文档注册 | 页面被嵌在 iframe 里（如聊天窗口内的 HTML 预览）时**不注册 SW**。SW 在嵌入式预览里本就没有意义，且安装失败态会拖住宿主界面。直接打开页面或安装为 PWA 均不受影响。 | 无需解决；这是刻意的守卫。**已在真实 iframe 中实测**：同源 SW 注册数为 0，应用照常渲染。 |
| SW 缓存缺项 | `sw.js` 采用逐项容错缓存，某个资源 404 不会导致离线能力整体失效，但该资源也就没有离线副本。 | 部署时确认 `ASSETS` 中每一项都能返回 2xx；`browser-check` 第 8 组会断言"清单 8 项一个没漏"。 |
| 数据未加密 | MVP 用 localStorage 明文存储。 | 正式版改用 SQLite + SQLCipher，密钥存 Keychain/Keystore。 |
| 无云端同步 | 数据仅存本地。 | 接入后端 + 端到端加密同步。 |
| 未做真机验证 | 在无头浏览器中验证了渲染与逻辑，未在 iOS/Android 真机上跑过。 | 上架前需补真机测试，尤其是各家 Android ROM 的后台保活与精确闹钟白名单。 |
| **无障碍未经真人验证** | 对比度/字号/点击区由数值断言验证，语义与焦点已用真实浏览器**计算后的 AX 树**核对（`a11y-tree.mjs`），但**仍未用读屏软件（TalkBack / VoiceOver）跑过，也没有真实的老年用户参与测试**。 | 上线前找 3–5 位真实 55+ 用户 + 一台开着 TalkBack 的测试机走一遍主流程。 |
| **省电收益未经仪器实测** | 自适应唤醒把轮询次数从"每秒 1 次"降到"临近 30 秒 / 空闲 5 分钟一次"（3 小时等待：10800 次 → 54 次），**这个数字是推算出来的，不是功耗仪测出来的**。 | 真机上用 Android Battery Historian 之类工具确认实际收益。 |
| 原生下另有耗电大头 | 轮询优化解决的是"应用存活期间的 CPU 唤醒"；原生容器里真正的耗电来自系统闹钟与常驻通知本身。 | 属设计取舍，需在真机上权衡「提醒必达」与「省电」。 |
| 隐私政策为应用内简述 | 免责声明与隐私政策均有真实弹层内容。隐私政策已按最新立场更新：**默认不联网**，唯一的例外是用户自己开启的家属协同（且事件不含药名与剂量）。 | 上架前需按各平台与法规要求补成正式隐私政策页面并托管到可公开访问的 URL（内容模板见 `../docs/06-部署与上架指南.md` §6）。 |

## 八、技术选型说明

最初评估过 Flutter，最终选择**「零依赖 PWA 内核 + Capacitor 原生容器」**：

| 阶段 | 做法 | 理由 |
|---|---|---|
| 内核 | 零依赖 PWA（本项目） | 起步环境没有 Flutter/Dart SDK，写一份编译不过的代码既无法交付也无法验收 |
| 投递 | Capacitor 包壳（`../native/`） | 只需换投递通道，业务代码零改动 |
| 已作废 | 重写 Flutter | 要把 1000+ 行 UI 全部重做，而收益并不在 UI 上 |

支撑这个取舍的是代码分层本身：

- `scheduler.js` 与 `platform.js` 是**平台无关的纯函数模块**，250 项测试覆盖，
  在浏览器与原生容器下跑的是同一份代码；
- 数据字段命名与 `docs/02` 的 SQL 表结构一一对应，迁移到 SQLite 只需替换
  `store.js` 的 `load/save`；
- 界面按移动端设计（375px 基准 + 小屏自动铺满），可直接作为原生版的 UI 规格。

换句话说：**先分层、再换实现**。这就是为什么平台抽象层要在移植之前先做。

详细取舍与真机验证清单见 `../docs/05-原生移植指南.md`。
